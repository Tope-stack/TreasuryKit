# 0007 — Reconciliation engine: decisions and deviations in Phase 3

- **Status:** Accepted
- **Date:** 2026-11-13

## Decisions

1. **Rules are synchronous.**
   - `IMatchingRule.Find(pool, parameters)` returns `IEnumerable<MatchCandidate>` rather than the `IAsyncEnumerable` + `CancellationToken` sketched in §5.2.
   - The engine is pure, in-memory domain code. All I/O happens before it runs, when the run handler loads the pool through Core's query contracts.
2. **Ties.**
   - Candidates are grouped by confidence, highest first. Within a group, a candidate that shares an item with another candidate wins nothing, and all its items are flagged `MultipleCandidates`.
   - Items involved in a tie are also unavailable to lower-confidence candidates in the same rule. A weaker candidate must not win just because two stronger ones cancelled each other out.
3. **`AmountDateWindow` scoring.**
   - Score = 0.80 + `0.10 × (1 − days ÷ (window + 1))` + `0.10 × similarity`, where the name term counts only when similarity ≥ `nameSimilarityMin`.
   - Without a counterparty name, the maximum is 0.90, so the rule only proposes.
   - "Exactly one candidate" is checked from both sides: the line's and the expected transaction's.
4. **Exceptions.**
   - **`Superseded` status:** this is an addition to §5.1's statuses. A rerun closes the open exceptions from earlier runs with this status, so reruns don't accumulate duplicates. Proposals from earlier runs are rejected with reason `Superseded`, as §5.4 specifies.
   - **Top-5 candidates:** a display score — amount closeness 0.5, date closeness 0.25 over a 30-day horizon, and name similarity 0.25 — plus a `referenceMatch` flag.
5. **Thresholds** live in `recon.settings` (one row per tenant). Rule configs and settings are seeded on `TenantCreated`, and filled in on first use for older tenants.
6. **Run periods and pool.**
   - **Lines:** those with value date in [from, to].
   - **Expected transactions:** loaded from [from − w, to + w], where w is the largest `windowDays` among enabled rules. Exceptions are raised only for those dated inside [from, to].
   - **Account:** expected transactions with no account take part in runs for any account in their currency.
7. **Concurrency.**
   - **One active run per account:** enforced by a partial unique index on (tenant, account) where status is `Queued` or `Running`. A losing request gets 409 with the active run's ID.
   - **`StatementImported` during an active run:** the active run is flagged with a widened follow-up period, and a new run is queued when it completes.
   - **Item uniqueness:** `recon.reconciled_items` is unique per item, so a race between two accounts over an unassigned expected transaction fails the second run's transaction. Its retry then excludes the item.
8. **Blocked runs** return **422** (`Run.Blocked`, `ErrorType.Failure`), not 400. The request is well-formed but refused by a business rule.
9. **Settlement.** `MatchConfirmed` is published for auto-confirmed matches. Core reduces `OutstandingAmount`, never below zero, logging a warning if it would. A `MatchReversed` handler already exists for Phase 4.

## Consequences

- The dataset in `tests/TestData/recon` (generated by `StatementGen --recon`) pins the expected outcome of every scenario. Changing the scoring or thresholds will show up there first.
- Phase 4 adds `SplitPayment` and `Tolerance` by registering more `IMatchingRule`s. Their configs are already seeded, and the engine skips rules that are not registered.
